# Deploy runbook — Options Signal Engine `2026.08.23`

Commits `6dab07d..7a2aa8a`. This release adds a published label, `CONFLICTED`,
that the currently-deployed database schema **rejects**.

> **ลำดับเดียวที่ถูก: migration ก่อน → app ทีหลัง เสมอ**

---

## 1. ทำไมลำดับนี้ถึงเป็นความเสี่ยงที่ร้ายแรงที่สุดใน release นี้

`public.options_signal_history.signal_type` มี CHECK constraint ที่ยังไม่รู้จักคำว่า
`CONFLICTED` ถ้า app ขึ้นก่อน migration:

1. ทุกการเขียนสัญญาณที่เป็น CONFLICTED ถูก Postgres ปฏิเสธด้วย SQLSTATE `23514`
2. `recordOptionsSignal` กลืน error นั้นไว้ตามการออกแบบ — ประวัติที่เขียนไม่ลง
   ไม่ใช่เหตุผลที่จะทำให้หน้าเว็บพัง
3. ผลคือประวัติ **หยุดสะสมเฉพาะหุ้นที่หลักฐานขัดกัน** หุ้นอื่นเขียนได้ตามปกติ

ข้อ 3 คือส่วนที่อันตราย baseline ของ percentile ตอนนี้ยังขาดอยู่
(**Put/Call ขาดอีก 19 วัน · IV ขาดอีก 59 วัน**) ถ้ามันโตขึ้นระหว่างที่หุ้นกลุ่ม
CONFLICTED หายไปเงียบๆ percentile ที่ได้จะมี **selection bias ฝังอยู่ในตัว**
และจะดูปกติทุกประการ — ตรวจจับยากกว่าข้อมูลหายทั้งก้อนมาก

พฤติกรรมนี้ไม่ใช่การคาดเดา — `history-migration.test.ts` รันบน Postgres จริง
แล้วยืนยันทั้งสองฝั่ง: ก่อน migration `CONFLICTED` โดนปฏิเสธด้วย `23514`
ขณะที่ `SIDEWAYS` ยังเขียนผ่าน

| # | ขั้น | คำสั่ง / การกระทำ | ผ่านเมื่อ |
|---|---|---|---|
| 0 | ตรวจก่อน | `npm run test && npm run typecheck && npm run lint` | เขียวทั้งหมด |
| 1 | **migration** | apply `supabase/migrations/202608230001_options_signal_history_conflicted_label.sql` | constraint ยอมรับ `CONFLICTED` |
| 2 | ยืนยัน migration | ดูข้อ 4 ด้านล่าง | คิวรีคืนค่าที่มี `CONFLICTED` |

**ช่วงระหว่างขั้น 1 กับ 3 จึงไม่มีความเสี่ยง** — ตรงข้ามกับลำดับกลับด้าน

## 3. Boot guard — สิ่งที่กันไว้ถ้าใครทำผิดลำดับ

`instrumentation.ts` เรียก `assertOptionsSignalSchemaReady()` หนึ่งครั้งตอน
สตาร์ทโปรเซส (Node runtime เท่านั้น) มันเขียน canary row ที่ติดป้าย
`CONFLICTED` ลงไปจริง แล้วดูว่า database ตอบว่าอะไร:

| คำตอบ | สถานะ | ผลกับการ boot |
|---|---|---|
| เขียนผ่าน | `ok` | สตาร์ทตามปกติ |
| ถูกปฏิเสธด้วย `23514` | `behind` | **throw ทันที** พร้อมชื่อไฟล์ migration ที่ต้องรัน |
| ถูกปฏิเสธด้วยเหตุอื่น / เขียนไม่ถึง / throw | `unknown` | สตาร์ทต่อ + `console.warn` |

`unknown` ไม่หยุด boot โดยตั้งใจ — service key หาย, database ยังไม่ตื่น,
เน็ตกระตุก ไม่ใช่หลักฐานว่า migration ยังไม่ได้รัน และการล้มทั้งระบบเพราะ
"ยังตอบไม่ได้" คือการแลกบั๊กเงียบมาเป็น outage ดังๆ ที่ไม่มีใครขอ

**ไม่มีทางลัดให้ข้าม guard นี้ และไม่มี fallback ที่จะเขียน SIDEWAYS แทน
CONFLICTED** ถ้ามีเมื่อไหร่ บั๊กแบบเดียวกันจะกลับมาในรูปที่ตรวจไม่เจอยิ่งกว่าเดิม

ข้อความที่ operator จะเห็นตอน boot ล้ม:

```
FATAL: the options_signal_history schema is behind this build (2026.08.23).
The database refuses signal_type "CONFLICTED": write:23514:new row for relation ...
Run the migration 202608230001_options_signal_history_conflicted_label.sql and start the app again.
The app is refusing to start ON PURPOSE. ...
```

## 5. CI/CD บังคับลำดับนี้อยู่หรือยัง — **ยัง**

ตรวจแล้ว: repo นี้ **ไม่มี `.github/workflows/` เลย** และ `railway.json`
คุม service `market-gateway` เท่านั้น (`startCommand: npm run gateway`)
ซึ่งไม่ใช่ Next app ที่รันเอนจินตัวนี้ ไม่มีที่ไหนใน repo ที่บังคับว่า
migration ต้องรันก่อน deploy

**สิ่งที่กันความเสี่ยงอยู่ตอนนี้คือ boot guard ในข้อ 3 ไม่ใช่ pipeline**
guard นั้นเปลี่ยน "เงียบและ bias" ให้เป็น "ไม่ยอมสตาร์ท" ซึ่งกู้คืนได้ทันที
แต่มันเป็นตาข่าย ไม่ใช่ลำดับ

ถ้าจะบังคับลำดับจริงๆ ต้องแก้ที่:

- **ถ้าใช้ Vercel** — เพิ่มขั้น migration เข้าไปใน build command
  (`supabase db push && next build`) หรือทำเป็น GitHub Action ที่รัน
  `supabase db push` แล้วค่อย trigger deployment ผ่าน deploy hook
- **ถ้าใช้ Railway สำหรับ Next app ด้วย** — เพิ่ม `preDeployCommand`
  ใน `railway.json` ของ service นั้น (คนละไฟล์กับ gateway)
- **ทางที่ไม่ต้องพึ่ง provider** — เพิ่ม `.github/workflows/deploy.yml`
  ที่มี job `migrate` แล้วให้ job `deploy` ประกาศ `needs: migrate`

ยังไม่ทำในรอบนี้เพราะไม่รู้ว่า Next app ถูก deploy ด้วยอะไร การเดาแล้วเขียน
pipeline ที่ไม่เคยรันลงไปจะแย่กว่าการเขียนไว้ว่ายังไม่มี

## 6. Rollback

### 6.1 ถ้าต้อง rollback app กลับเป็นเวอร์ชันก่อนหน้า — **ทำได้**

ปล่อย migration ค้างไว้ **อย่า revert** CHECK constraint บังคับตอน **เขียน**
เท่านั้น ไม่ได้บังคับตอนอ่าน ดังนั้น app เก่าที่เจอแถวที่เป็น `CONFLICTED`:

- **ไม่มีโค้ดฝั่ง app อ่าน `signal_type` กลับมาเลย** ตรวจแล้วทั้ง repo:
  `toPoint()` ใน `signal-history-repository.ts` map เฉพาะ `captured_at`,
  `config_version`, `iv`, `put_call_oi`, `put_call_volume` — คอลัมน์นี้เขียน
  อย่างเดียว เก็บไว้เป็นบันทึก ไม่ได้เข้า runtime path ไหน
- เปอร์เซ็นไทล์จึงไม่กระทบ แถวที่เป็น CONFLICTED ยังนับเข้า baseline ตามปกติ
  เพราะมันอ่านสามคอลัมน์ตัวเลข ไม่ได้อ่านป้าย
- app เก่าเขียนทับวันเดียวกันได้ตามปกติ (upsert บน `symbol, captured_at`)
  แล้วป้ายจะกลับเป็น `SIDEWAYS` ของเอนจินเก่า ซึ่งถูกต้องสำหรับเวอร์ชันนั้น
- `summary.signalType` บนการ์ดมาจากการคำนวณสดทุกครั้ง ไม่ได้มาจากตารางนี้
  เอนจินเก่าจึงไม่มีทางผลิตคำว่า CONFLICTED ออกมาให้ตัวเองต้องแสดง

ข้อควรรู้เผื่ออนาคต: ถ้ามีใครทำให้ `signal_type` ถูกอ่านกลับมาแล้วส่งเข้า
การ์ด rollback จะไม่ปลอดภัยอีกต่อไป — `OptionsSignalSection.tsx:191` ใน build
ก่อนหน้าเขียนว่า `OPTIONS_SIGNAL_PRESENTATION[summary.signalType]` แล้วอ่าน
`.tone` ต่อทันที โดยไม่ป้องกัน key ที่ไม่รู้จัก ป้ายที่ไม่มีใน map จะกลายเป็น
`undefined` แล้ว throw ตอน render ตอนนี้ยังไม่เป็นปัญหาเพราะไม่มีเส้นทางนั้นอยู่

### 6.2 ถ้าอยาก revert migration — **อย่า ตราบใดที่ app ใหม่ยังรันอยู่**

การหด CHECK กลับใต้ app ใหม่คือการสร้างสถานการณ์เดียวกับที่ทั้งเอกสารนี้
เขียนขึ้นมาเพื่อป้องกัน และคราวนี้ boot guard จะไม่ช่วย เพราะโปรเซสสตาร์ทไปแล้ว
ถ้าจำเป็นจริงๆ ต้อง rollback app ก่อน แล้วค่อย revert และต้องลบแถวที่เป็น
`CONFLICTED` ออกก่อน ไม่งั้น `alter table ... add constraint` จะล้มเพราะ
แถวเดิมละเมิด constraint ใหม่

```sql
-- ทำตามลำดับนี้เท่านั้น และหลังจาก rollback app แล้วเท่านั้น
delete from public.options_signal_history where signal_type = 'CONFLICTED';
alter table public.options_signal_history
  drop constraint options_signal_history_signal_type_check;
alter table public.options_signal_history
  add constraint options_signal_history_signal_type_check
  check (signal_type in ('PRIME_CALL','CALL_WATCH','SIDEWAYS','PUT_WATCH','PRIME_PUT','IV_WARNING'));
```

`delete` ตรงนั้นทิ้งประวัติจริงไป ซึ่งเป็นราคาของการ revert และเป็นอีกเหตุผล
